# Milestone: Prototype 01 — Continuous World

Status: **Planned**

## 1. Purpose

Prototype 01 exists to answer one question:

> Can Progressus support a deterministic, persistent, effectively unbounded physical world containing characters, jobs, resources, construction, and simple production without depending on a finite prebuilt map or graphical UI?

It is a technical/gameplay proof, not a vertical slice of the final game.

## 2. Player-visible scenario

A new game starts with five characters in a small generated area.

The player can:

1. inspect the nearby terrain;
2. designate basic resource collection;
3. create a stockpile;
4. build a simple work structure/workbench;
5. craft at least one useful tool or product from physical inputs;
6. order characters to travel beyond initially generated terrain;
7. see new chunks appear continuously;
8. save;
9. quit;
10. load and continue from the same authoritative state.

The prototype does not need polished graphics or final UX.

## 3. Required world systems

### P01-WORLD-01 — Seeded world

New games receive or accept a world seed.

The same seed + worldgen version + chunk coordinate must generate the same untouched chunk.

### P01-WORLD-02 — Chunked generation

Terrain is generated by fixed-size chunks on demand.

Generating chunks in different visitation orders must not change canonical untouched terrain.

### P01-WORLD-03 — Arbitrary traversal

A character can move across many chunk boundaries in positive and negative coordinates without encountering a designed map edge.

The acceptance test should cover enough distance to catch hidden finite-grid assumptions.

**Partially advanced (bootstrap):** deterministic fixed-point cardinal movement crosses the immediate positive and negative chunk boundaries, and the external headless walker crosses 64 positive boundaries without a finite global grid or preloaded route. Long-distance traversal across both signs, chunk residency, and general navigation remain incomplete.

### P01-WORLD-04 — Sparse residency

The implementation must not require all generated or visited chunks to remain loaded in memory.

A simple unload policy is sufficient.

**Incomplete:** no resident caching or unload policy exists yet.

### P01-WORLD-05 — Modified world state

Changes to terrain or placed objects in a chunk persist independently of deterministic base generation.

**Partially advanced (bootstrap):** deterministic base terrain remains immutable while `Simulation` holds sparse, in-memory effective-terrain overrides. Movement and terrain snapshots observe the effective terrain. Save/load, chunk residency, placed objects, and terrain gameplay commands remain incomplete.

## 4. Required simulation systems

### P01-SIM-01 — Deterministic simulation clock

The authoritative simulation advances in discrete steps independent of renderer frame rate.

Headless stepping is supported.

### P01-SIM-02 — Stable entity IDs

Characters and persistent world objects receive stable identities that survive save/load.

### P01-SIM-03 — Five characters

A new scenario creates five controllable/simulatable characters.

Minimum runtime state:

- ID;
- name;
- world position;
- current task;
- movement state.

Other needs/skills may remain minimal.

### P01-SIM-04 — Movement

Characters can navigate walkable generated terrain and cross chunk boundaries.

Pathfinding must not require a single finite global grid.

**Partially advanced (bootstrap):** characters retain `Idle`, persistent cardinal direction, or private `Navigating` state and carry an authoritative `WorldPosition` with signed integer `1024`-subunit precision. The bootstrap speed is `256` subunits/tick; one tick may advance within a cell, while higher speeds can cross several sequentially checked cells. A bounded deterministic cardinal A* finds an effective-terrain route without a finite global map; player `MoveTo` is additionally restricted to the monotonically discovered world and cannot use unknown cells as a hidden shortcut. It follows exact fixed-point waypoints, rechecks every cell transition, and stops at the canonical boundary if terrain becomes blocked. Per-tick traces reset to the current exact position before movement, so an idle character does not retain a stale arrival trace. Commands and detached exact-position/selected-route snapshots cross `progressus-app`; a bounded headless walker proves 64 positive chunk-boundary crossings while preserving character ID. This is still bootstrap navigation, not complete navigation: no diagonal or hierarchical search, auto-repath, generalized jobs/AI priority policy, collision/physical footprint, speed modifiers, chunk residency, or persistence exists. Harvest and Haul jobs now reuse this movement layer and release reservations on explicit player interruption; in-transit haul items are dropped at the worker position before the manual command takes over.

### P01-SIM-05 — Jobs

At least these job categories must exist conceptually:

- collect/harvest resource;
- haul resource;
- construct;
- craft.

Jobs have explicit lifecycle and reservation/cancellation behavior.

**Partially advanced (bootstrap):** `Harvest`, `Haul`, and `Craft` are implemented job categories. Jobs have stable identity and exclusive worker reservations; Harvest adds source reservation and `Available -> Reserved -> Working`, Haul additionally reserves one physical item and one destination cell and uses `Available -> Reserved -> Transporting`, and Craft reserves one workbench plus the concrete physical input stack IDs it will consume. Assignment is deterministic, all three categories reuse bounded navigation where needed, and cancellation/manual interruption clean reservations. Harvest depletes a source into a physical stack; Haul preserves that stack through `Ground -> Carried -> Ground`; Craft consumes exact quantities and creates one physical output stack. Construct jobs remain incomplete.

### P01-SIM-06 — No duplicate ownership

A physical item/stack cannot simultaneously be on the ground, carried, and stored.

This invariant requires automated tests.

**Partially advanced (bootstrap):** physical `Wood` and `Stone` stacks have global stable Progressus IDs and exactly one authoritative `ItemLocation::{Ground, Carried}` state. Ground stacks use exact fixed-point `WorldPosition`, a chunk-aware ground index, and atomic reach-checked pickup/drop transitions. Haul jobs now exercise the full ownership transition `Ground → Carried → Ground` while preserving ID, kind, and quantity; cancellation tests cover reservation cleanup and dropping an in-transit stack. Stockpile floor areas deliberately do not add a fake stored state. Compatible ground stacks now merge deterministically during Haul delivery up to the hard 1,024-unit capacity. Real containers, stack splitting, consumption/destruction, and persistence remain incomplete.

## 5. Required resource and production systems

Prototype content should remain intentionally tiny.

Minimum resource set:

- wood;
- stone;
- one food resource if useful for scenario feedback.

Minimum production chain:

```text
world resource
   ↓
collection
   ↓
physical stockpile
   ↓
workbench / work site
   ↓
recipe
   ↓
physical crafted output
```

A suggested first chain is:

```text
wood + stone
    ↓
primitive tool
```

The exact recipe is not important. The physical flow is.

**Partially advanced (bootstrap):** a new seed starts with four deterministic physical Wood/Stone supply stacks at distinct sub-cell positions. Untouched worldgen provides deterministic grass-only `Tree` and `StoneOutcrop` source cells with finite yields. Sources can be designated for harvest: a deterministically selected worker reserves the job, travels, performs fixed work, depletes the source, and creates one physical Wood/Stone stack preserving the configured yield. Stockpile areas can be designated on valid explored ground; deterministic haul jobs reserve one item/worker/destination and physically carry eligible stacks into compatible or empty stockpile cells. Same-kind deliveries merge up to 1,024 units while preserving the destination stack identity. A bootstrap Workbench now runs the first typed Craft recipe, `2 Wood + 1 Stone -> 1 PrimitiveTool`: it reserves concrete nearby stockpile stack IDs, consumes exact quantities, and creates a normal physical output stack that can be hauled. Tests cover Harvest→Haul integration, stack merging, Craft reservation/consumption/output, multi-item destination exclusivity, manual interruption, and workstation removal cleanup. Workbench placement itself is still instantaneous; physical construction, stockpile filters/priorities, containers, and richer recipe/order policy remain incomplete.

## 6. Required construction

The player can designate at least:

- stockpile area;
- workbench/work site;
- one simple built structure or object.

Construction requires physical materials and work. A building must not become complete merely because required resources exist elsewhere on the map.

## 7. Persistence

### P01-SAVE-01 — Versioned save metadata

Every save records at least:

- save format version;
- world seed;
- worldgen version;
- simulation time.

### P01-SAVE-02 — Entity persistence

Persistent entities preserve IDs and authoritative state across save/load.

### P01-SAVE-03 — Chunk persistence

Untouched chunks may be regenerated. Modified chunks must reconstruct their modifications correctly.

### P01-SAVE-04 — Explicit incompatibility

An unsupported save version must fail with a clear error. Silent best-effort corruption is forbidden.

## 8. Headless test requirements

Prototype 01 is not accepted solely because it is playable in a window.

Required automated or scripted checks:

### TEST-P01-01 — Worldgen repeatability

Generate selected chunks twice from the same seed and compare authoritative terrain/resource data.

### TEST-P01-02 — Generation order independence

Generate a set of neighboring chunks in two different orders. Results must match per coordinate.

### TEST-P01-03 — Cross-chunk travel

Move an entity across multiple chunk boundaries and verify final position and identity.

**Partially advanced:** simulation tests cover manual and routed `x=31 -> x=32` and manual `x=0 -> x=-1` with the same `EntityId` at fixed-point resolution; the headless application-boundary scenario drives ID 3 across 64 positive chunk boundaries for seed 0, under current worldgen v2 ending at coarse cell `(2048, 89)` after 2,239 chosen-cell steps (8,956 default-speed ticks). Long-distance negative traversal and residency/unload behavior remain future coverage.

### TEST-P01-04 — Item ownership invariant

Exercise pickup, hauling, storage, crafting consumption, cancellation, and entity interruption without duplicating or losing items outside explicit rules.

### TEST-P01-05 — Save/load round trip

Create a modified world state, save, load, and compare authoritative state.

### TEST-P01-06 — Distant modified chunks

Modify at least two widely separated chunks, unload them, reload them, and verify both modifications.

### TEST-P01-07 — Long-run smoke test

Run the simulation headlessly for a large number of ticks with basic activity and ensure:

- no crash;
- no invariant violation;
- bounded loaded-chunk count under the chosen policy;
- no obvious runaway job/resource duplication.

The exact tick count should be chosen once simulation speed is measurable.

## 9. UI requirements

Only enough interface is required to operate and inspect the prototype.

**Partially advanced (bootstrap):** the native Bevy client opens seed `0`, renders five snapshot-driven characters and the explored terrain intersecting its camera viewport plus a small margin, accepts Cora's arrow/Stop movement input plus left-click selection and right-click exact `MoveTo`, and provides presentation-only pan/zoom. The selected character is visibly bracketed and its route/destination are shown by default; F3 adds only the technical authoritative-position overlay. A bottom toolbar provides Select, Stockpile add/remove, Harvest, Workbench, Craft tool, and Cancel-jobs tools. Stockpile/harvest/cancel designations operate over a dragged rectangular cell area with a live grid preview; Workbench and Craft are point tools, and right-click or Escape returns to Select. Shift+left-click harvest and Ctrl+left-click single-cell stockpile editing remain temporary shortcuts. The camera itself does not discover terrain; unknown cells remain background and snapshots do not expose their terrain type. Selected sprite interpolation follows the latest detached per-tick motion-trace polyline without restarting for repeat snapshots of the same simulation tick. Terrain/item presentation refreshes on authoritative revisions rather than every render frame. The client renders physical Wood/Stone/PrimitiveTool ground stacks with procedural pixel quantity labels, natural resources, workbenches, harvest/craft designations, stockpile-cell outlines, and carried stacks parented to worker visuals while hauling. The remaining interface, richer navigation, generalized jobs/AI controls, speed/collision, persistence, residency, physical construction, stockpile policies, containers, and save/load criteria are incomplete.

Minimum capabilities:

- pan/zoom camera;
- select a character;
- inspect basic character state;
- designate resource gathering;
- designate a stockpile;
- place a workbench/building;
- request a recipe/order;
- pause and resume;
- save/load.

Debug overlays are more valuable than visual polish at this stage.

Useful overlays include:

- chunk boundaries and coordinates;
- loaded/active chunk state;
- entity IDs;
- current jobs/reservations;
- pathfinding route;
- item ownership/location.

## 10. Non-goals

Prototype 01 explicitly does **not** require:

- deep needs or mood;
- relationships;
- families;
- combat;
- enemies;
- research tree;
- agriculture simulation;
- metallurgy;
- electricity;
- vehicles;
- roads;
- multiple settlements;
- Simulation LOD aggregation;
- weather simulation;
- advanced water simulation;
- final art;
- final sound;
- mod support;
- multiplayer.

If one of these becomes necessary to prove a core invariant, document why before implementing it.

## 11. Performance evidence

Prototype 01 should establish baseline measurements, not ambitious final targets.

Record at minimum:

- world generation time per chunk distribution;
- loaded chunk memory estimate;
- simulation ticks per second in headless mode;
- pathfinding cost in representative local scenarios;
- save size for a sparse world with distant modified chunks;
- save and load duration.

Numbers are evidence for later architecture decisions, not pass/fail targets unless a catastrophic bottleneck makes the prototype unusable.

## 12. Definition of done

Prototype 01 is complete when all of the following are true:

- [ ] one command can run the automated test suite;
- [ ] one command can run a headless simulation scenario;
- [ ] a playable client can create a world from a seed;
- [ ] five characters exist as stable persistent entities;
- [ ] resource collection and hauling work;
- [ ] physical stockpiling works;
- [ ] construction consumes delivered physical inputs;
- [ ] crafting consumes inputs and creates an output;
- [ ] characters can traverse far enough to prove chunk streaming;
- [ ] distant chunks can unload and reload;
- [ ] save/load round trip preserves authoritative state;
- [ ] worldgen determinism/order-independence tests pass;
- [ ] no known item duplication bug exists;
- [ ] long-run headless smoke test passes;
- [ ] baseline performance measurements are documented;
- [ ] architecture documentation matches the implementation.

## 13. What comes next

Prototype 02 should turn this technical foundation into a sustainable small settlement by introducing food production/consumption, sleep/shelter, skills, simple research, mining, and early metallurgy.

Prototype 03 is where Progressus must prove its most important scale transition: multiple physically connected settlements, transport routes, larger populations, and the first real Simulation LOD.

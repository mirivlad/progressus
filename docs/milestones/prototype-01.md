# Milestone: Prototype 01 — Continuous World

Status: **Planned**

## 1. Purpose

Prototype 01 exists to answer one question:

> Can Progressus support a deterministic, persistent, effectively unbounded physical world containing characters, jobs, resources, construction, and simple production without depending on a finite prebuilt map or graphical UI?

It is a technical/gameplay proof, not a vertical slice of the final game.

## 2. Player-visible scenario

A new game starts with five characters in a small generated area.

The player can:

1. inspect the nearby terrain;
2. designate basic resource collection;
3. create a stockpile;
4. build a simple work structure/workbench;
5. craft at least one useful tool or product from physical inputs;
6. order characters to travel beyond initially generated terrain;
7. see new chunks appear continuously;
8. save;
9. quit;
10. load and continue from the same authoritative state.

The prototype does not need polished graphics or final UX.

## 3. Required world systems

### P01-WORLD-01 — Seeded world

New games receive or accept a world seed.

The same seed + worldgen version + chunk coordinate must generate the same untouched chunk.

### P01-WORLD-02 — Chunked generation

Terrain is generated by fixed-size chunks on demand.

Generating chunks in different visitation orders must not change canonical untouched terrain.

### P01-WORLD-03 — Arbitrary traversal

A character can move across many chunk boundaries in positive and negative coordinates without encountering a designed map edge.

The acceptance test should cover enough distance to catch hidden finite-grid assumptions.

**Advanced bootstrap:** deterministic fixed-point cardinal movement crosses the immediate positive and negative chunk boundaries, and the external headless walker crosses 64 positive boundaries without a finite global grid or preloaded route. Character-centered radius-one chunk residency now remains bounded during that route (21 resident chunks at the end and a maximum of 21 with five characters). Long-distance traversal across both signs and general navigation remain incomplete.

### P01-WORLD-04 — Sparse residency

The implementation must not require all generated or visited chunks to remain loaded in memory.

A simple unload policy is sufficient.

**Implemented bootstrap:** raw deterministic `GeneratedChunk` values are a derived cache centered on authoritative character chunks. Each distinct character chunk requests a 3×3 radius-one neighborhood; overlaps deduplicate, camera/read-only queries outside the set are ephemeral, and chunks leaving the union are discarded. Sparse authoritative modifications remain outside the cache and survive unload/reload. Save v1 does not serialize residency and reconstructs it from restored character positions. See [`ADR-0015`](../adr/0015-character-centered-derived-chunk-residency.md).

### P01-WORLD-05 — Modified world state

Changes to terrain or placed objects in a chunk persist independently of deterministic base generation.

**Advanced bootstrap:** deterministic base terrain remains immutable while `Simulation` holds sparse effective-terrain overrides. Movement and terrain snapshots observe the effective terrain; save v1 round-trips distant overrides, and the residency regression explicitly moves between two far-apart modified chunks, unloads each raw chunk, and verifies the modifications after regeneration. Placed objects are persistent authoritative entities, while a terrain gameplay editing command remains incomplete.

## 4. Required simulation systems

### P01-SIM-01 — Deterministic simulation clock

The authoritative simulation advances in discrete steps independent of renderer frame rate.

Headless stepping is supported.

### P01-SIM-02 — Stable entity IDs

Characters and persistent world objects receive stable identities that survive save/load.

### P01-SIM-03 — Five characters

A new scenario creates five controllable/simulatable characters.

Minimum runtime state:

- ID;
- name;
- world position;
- current task;
- movement state.

Other needs/skills may remain minimal.

### P01-SIM-04 — Movement

Characters can navigate walkable generated terrain and cross chunk boundaries.

Pathfinding must not require a single finite global grid.

**Partially advanced (bootstrap):** characters retain `Idle`, persistent cardinal direction, or private `Navigating` state and carry an authoritative `WorldPosition` with signed integer `1024`-subunit precision. The bootstrap speed is `256` subunits/tick; one tick may advance within a cell, while higher speeds can cross several sequentially checked cells. A bounded deterministic cardinal A* finds an effective-terrain route without a finite global map; player `MoveTo` is additionally restricted to the monotonically discovered world and cannot use unknown cells as a hidden shortcut. It follows exact fixed-point waypoints, rechecks every cell transition, and stops at the canonical boundary if terrain becomes blocked. Per-tick traces reset to the current exact position before movement, so an idle character does not retain a stale arrival trace. Commands and detached exact-position/selected-route snapshots cross `progressus-app`; a bounded headless walker proves 64 positive chunk-boundary crossings while preserving character ID. This is still bootstrap navigation, not complete navigation: no diagonal or hierarchical search, auto-repath, generalized jobs/AI priority policy, collision/physical footprint, speed modifiers, or chunk residency exists. Harvest and Haul jobs now reuse this movement layer and release reservations on explicit player interruption; in-transit haul items are dropped at the worker position before the manual command takes over.

### P01-SIM-05 — Jobs

At least these job categories must exist conceptually:

- collect/harvest resource;
- haul resource;
- construct;
- craft.

Jobs have explicit lifecycle and reservation/cancellation behavior.

**Advanced (bootstrap):** `Harvest`, `Haul`, `Craft`, `DeliverConstruction`, and `Construct` are implemented job categories. Jobs have stable identity and exclusive worker reservations; Harvest adds source reservation, Haul reserves one physical item and one destination cell, Craft reserves one workbench plus concrete physical input stack IDs, and construction reserves one site plus its concrete material stack. Assignment is deterministic, all categories reuse bounded navigation where needed, and cancellation/manual interruption clean reservations. Harvest depletes a source into a physical stack; Haul preserves that stack through `Ground -> Carried -> Ground`; Craft consumes exact quantities and creates one physical output stack; construction physically delivers material before work and then converts the stable-ID site into a blocking structure.

### P01-SIM-06 — No duplicate ownership

A physical item/stack cannot simultaneously be on the ground, carried, and stored.

This invariant requires automated tests.

**Partially advanced (bootstrap):** physical `Wood` and `Stone` stacks have global stable Progressus IDs and exactly one authoritative `ItemLocation::{Ground, Carried}` state. Ground stacks use exact fixed-point `WorldPosition`, a chunk-aware ground index, and atomic reach-checked pickup/drop transitions. Haul jobs now exercise the full ownership transition `Ground → Carried → Ground` while preserving ID, kind, and quantity; cancellation tests cover reservation cleanup and dropping an in-transit stack. Stockpile floor areas deliberately do not add a fake stored state. Compatible ground stacks now merge deterministically during Haul delivery up to the hard 1,024-unit capacity. Real containers and player-directed/general-purpose stack splitting remain incomplete; item identity/location/quantity now round-trip through save format v1.

## 5. Required resource and production systems

Prototype content should remain intentionally tiny.

Minimum resource set:

- wood;
- stone;
- one food resource if useful for scenario feedback.

Minimum production chain:

```text
world resource
   ↓
collection
   ↓
physical stockpile
   ↓
workbench / work site
   ↓
recipe
   ↓
physical crafted output
```

A suggested first chain is:

```text
wood + stone
    ↓
primitive tool
```

The exact recipe is not important. The physical flow is.

**Partially advanced (bootstrap):** a new seed starts with four deterministic physical Wood/Stone supply stacks at distinct sub-cell positions. Untouched worldgen provides deterministic grass-only `Tree` and `StoneOutcrop` source cells with finite yields. Sources can be designated for harvest: a deterministically selected worker reserves the job, travels, performs fixed work, depletes the source, and creates one physical Wood/Stone stack preserving the configured yield. Stockpile areas can be designated on valid explored ground; deterministic haul jobs reserve one item/worker/destination and physically carry eligible stacks into compatible or empty stockpile cells. Haul now prefers a compatible partial stack before an empty cell and can physically consolidate same-kind stacks already inside a stockpile in a canonical non-ping-pong direction. Same-kind deliveries merge up to 1,024 units while preserving the destination stack identity. A bootstrap Workbench now runs the first typed Craft recipe, `2 Wood + 1 Stone -> 1 PrimitiveTool`, through stable production orders with finite or infinite targets. Each active craft consumes concrete stack IDs from its producer's Input zone. Missing quantities are split exactly from distant stockpiled stacks and physically delivered by `SupplyProduction`; Craft creates its physical output in the producer's Output zone, from which ordinary Haul can return it to storage. Competing workbenches cannot reserve the same physical input, and a two-workbench infinite-order regression verifies that a waiting station receives the next shared input instead of starving. Tests cover Harvest→Haul integration, stack merging, Craft reservation/consumption/output, production-order repetition, shared-input arbitration, multi-item destination exclusivity, manual interruption, and workstation removal cleanup. A first physical construction chain is now implemented: `StoneWall` reserves one concrete Stone stack, carries it to an accessible position beside the site, performs fixed work, consumes exactly 2 Stone, and converts the site into a finished movement/A* blocker while preserving the site ID. Workbench placement itself is still instantaneous; demolition, doors, stockpile filters/priorities, containers, stock-target production orders, and richer order policy remain incomplete.

## 6. Required construction

The player can designate at least:

- stockpile area;
- workbench/work site;
- one simple built structure or object.

Construction requires physical materials and work. A building must not become complete merely because required resources exist elsewhere on the map.

**Implemented bootstrap:** `StoneWall` satisfies this invariant through `ConstructionSite -> DeliverConstruction -> Construct -> Structure`. Material is a reserved physical Stone stack, is visibly carried and dropped beside the site, and only then can construction consume 2 Stone. Finished walls block both movement and A* without rewriting base terrain. Cancellation drops in-transit material and removes the site/reservations. See [`ADR-0009`](../adr/0009-physical-construction-sites-and-blocking-structures.md).

## 7. Persistence

### P01-SAVE-01 — Versioned save metadata

Every save records at least:

- save format version;
- world seed;
- worldgen version;
- simulation time.

### P01-SAVE-02 — Entity persistence

Persistent entities preserve IDs and authoritative state across save/load.

### P01-SAVE-03 — Chunk persistence

Untouched chunks may be regenerated. Modified chunks must reconstruct their modifications correctly.

### P01-SAVE-04 — Explicit incompatibility

An unsupported save version must fail with a clear error. Silent best-effort corruption is forbidden.

**Implemented bootstrap:** save format v1 records seed, worldgen version, tick, next stable ID, exact character/navigation state, sparse terrain overrides, exploration, depleted resources, physical items and carriers, stockpiles, workstations, finite/infinite production orders, Input/Output logistics, construction, active jobs, and reservation state. Untouched generated chunks are omitted and regenerated. Unsupported versions, malformed references, and duplicate IDs fail explicitly. `progressus-app` exposes save/load without leaking `Simulation`; the native client adds three localized desktop slots with recoverable temporary/backup replacement and swaps the running application only after full validation. Deterministic continuation tests save during active production/navigation and prove byte-identical authoritative continuation after load. See [`ADR-0014`](../adr/0014-client-save-slots-and-atomic-load.md).

## 8. Headless test requirements

Prototype 01 is not accepted solely because it is playable in a window.

Required automated or scripted checks:

### TEST-P01-01 — Worldgen repeatability

Generate selected chunks twice from the same seed and compare authoritative terrain/resource data.

### TEST-P01-02 — Generation order independence

Generate a set of neighboring chunks in two different orders. Results must match per coordinate.

### TEST-P01-03 — Cross-chunk travel

Move an entity across multiple chunk boundaries and verify final position and identity.

**Advanced bootstrap:** simulation tests cover manual and routed `x=31 -> x=32` and manual `x=0 -> x=-1` with the same `EntityId` at fixed-point resolution; the headless application-boundary scenario drives ID 3 across 64 positive chunk boundaries for seed 0, under current worldgen v2 ending at coarse cell `(2048, 89)` after 2,239 chosen-cell steps (8,956 default-speed ticks). The same run validates that every character remains in a resident chunk and that the resident count stays within the `9 × character_count` policy. Long-distance negative traversal remains future coverage.

### TEST-P01-04 — Item ownership invariant

Exercise pickup, hauling, storage, crafting consumption, cancellation, and entity interruption without duplicating or losing items outside explicit rules.

### TEST-P01-05 — Save/load round trip

Create a modified world state, save, load, and compare authoritative state.

### TEST-P01-06 — Distant modified chunks

Modify at least two widely separated chunks, unload them, reload them, and verify both modifications.

**Implemented:** a simulation regression modifies chunks `(800,-900)` and `(-1200,1400)`, moves the full character interest set between them, proves the previous raw chunk leaves residency, and verifies each sparse override before, during, and after regeneration.

### TEST-P01-07 — Long-run smoke test

Run the simulation headlessly for a large number of ticks with basic activity and ensure:

- no crash;
- no invariant violation;
- bounded loaded-chunk count under the chosen policy;
- no obvious runaway job/resource duplication.

The current headless smoke advances 100,000 ticks and validates the residency bound through `progressus-app`; travel64 additionally checks the bound during 8,956 movement ticks. A future activity-heavy long-run scenario should add sustained production/construction load.

## 9. UI requirements

Only enough interface is required to operate and inspect the prototype.

**Partially advanced (bootstrap):** the native Bevy client opens seed `0`, renders five snapshot-driven characters and the explored terrain intersecting its camera viewport plus a small margin, accepts Cora's arrow/Stop movement input plus left-click selection and right-click exact `MoveTo`, and provides presentation-only pan/zoom. A localized toolbar control and `P` pause/resume authoritative ticks without accumulating scheduler backlog; map/UI commands remain usable while paused. The selected character is visibly bracketed and its route/destination are shown by default; F3 shows the resident-chunk outline and, for a selected character, the technical authoritative-position cross. A bottom toolbar provides Select, Stockpile add/remove, Harvest, Stone wall, Workbench, and Cancel-jobs tools. Stockpile/harvest/wall/cancel designations operate over a dragged rectangular cell area with a live grid preview; Workbench is a point placement tool, and right-click or Escape returns to Select. In Select mode, clicking a workbench opens the reusable modal workstation inspector. That modal lists recipes and authoritative production orders, supports finite quantity adjustment plus an explicit infinite `∞` target, deletion and workstation removal, and shows a logistics schematic. A Workbench owns exactly two red-marked cardinal Input ports and two yellow-marked diagonal Output ports. Separate localized rotate actions cycle each pair independently through its six canonical layouts; Workbench logistics cells are no longer painted individually. The modal can be closed with Escape. The localization layer ships Russian and English UI strings with Russian as the default and a toolbar language toggle; the client resolves a system font with Cyrillic coverage because Bevy's embedded subset is ASCII-only. Shift+left-click harvest and Ctrl+left-click single-cell stockpile editing remain temporary shortcuts. The camera itself does not discover terrain; unknown cells remain background and snapshots do not expose their terrain type. Every character sprite interpolates from its detached last-tick motion-trace polyline without restarting for repeat snapshots of the same simulation tick; selecting a character is required only for publishing its route/destination, not for smooth movement. Terrain/item presentation refreshes on authoritative revisions rather than every render frame. The client renders physical Wood/Stone/PrimitiveTool ground stacks with procedural pixel quantity labels, natural resources, workbenches, construction blueprints/finished stone walls, harvest/construction designations, stockpile-cell outlines, and carried stacks parented to worker visuals during hauling or construction delivery. F3 now also outlines the current resident chunk set while keeping the selected character's authoritative-position cross. The remaining interface, richer navigation, generalized jobs/AI controls, speed/collision, demolition/doors, stockpile policies, containers, autosaves, and richer save-management criteria are incomplete. Pause is client runtime state rather than save data: loading a slot preserves whether the player paused the session and only resets the partial tick timer.

Minimum capabilities:

- pan/zoom camera;
- select a character;
- inspect basic character state;
- designate resource gathering;
- designate a stockpile;
- place a workbench/building;
- request a recipe/order;
- pause and resume;
- save/load.

Debug overlays are more valuable than visual polish at this stage.

Useful overlays include:

- chunk boundaries and coordinates;
- loaded/active chunk state;
- entity IDs;
- current jobs/reservations;
- pathfinding route;
- item ownership/location.

## 10. Non-goals

Prototype 01 explicitly does **not** require:

- deep needs or mood;
- relationships;
- families;
- combat;
- enemies;
- research tree;
- agriculture simulation;
- metallurgy;
- electricity;
- vehicles;
- roads;
- multiple settlements;
- Simulation LOD aggregation;
- weather simulation;
- advanced water simulation;
- final art;
- final sound;
- mod support;
- multiplayer.

If one of these becomes necessary to prove a core invariant, document why before implementing it.

## 11. Performance evidence

Prototype 01 should establish baseline measurements, not ambitious final targets.

Record at minimum:

- world generation time per chunk distribution;
- loaded chunk memory estimate;
- simulation ticks per second in headless mode;
- pathfinding cost in representative local scenarios;
- save size for a sparse world with distant modified chunks;
- save and load duration.

Numbers are evidence for later architecture decisions, not pass/fail targets unless a catastrophic bottleneck makes the prototype unusable.

## 12. Definition of done

Prototype 01 is complete when all of the following are true:

- [ ] one command can run the automated test suite;
- [ ] one command can run a headless simulation scenario;
- [ ] a playable client can create a world from a seed;
- [ ] five characters exist as stable persistent entities;
- [ ] resource collection and hauling work;
- [ ] physical stockpiling works;
- [x] construction consumes delivered physical inputs;
- [ ] crafting consumes inputs and creates an output;
- [x] characters can traverse far enough to prove chunk streaming;
- [x] distant chunks can unload and reload;
- [x] save/load round trip preserves authoritative state;
- [x] worldgen determinism/order-independence tests pass;
- [ ] no known item duplication bug exists;
- [ ] long-run headless smoke test passes;
- [ ] baseline performance measurements are documented;
- [ ] architecture documentation matches the implementation.

## 13. What comes next

Prototype 02 should turn this technical foundation into a sustainable small settlement by introducing food production/consumption, sleep/shelter, skills, simple research, mining, and early metallurgy.

Prototype 03 is where Progressus must prove its most important scale transition: multiple physically connected settlements, transport routes, larger populations, and the first real Simulation LOD.
